# Request/response state IDs

Request operations return local state IDs rather than communication metadata:

| Operation | Successful result |
| --- | --- |
| `sendRequest`, `sendRequestAuthenticated` | `(networkMessageHandle, clientStateId)` |
| `receiveRequest`, `receiveRequestAuthenticated` | `(requestPayload, serverStateId)` |
| `sendResponse server serverStateId response` | Network message handle |
| `receiveResponse client clientStateId messageHandle` | Response payload |
| `receiveResponseAuthenticated client clientStateId messageHandle` | Response payload, after checking the retained authenticated identity |

A state ID is scoped to its participant and `CommunicationState α` type. It is
not a trace timestamp or a network message handle. Response operations recover
the key, identities, and original request internally from the retained state.
Missing IDs, wrong state variants, and invalid cryptographic responses fail.

The trace configuration uses
`PersistentLocalUpdateableState.CompromisableState (CommunicationState α)`.
`communicationStateInv` requires equal values on subsequent writes to an
existing address. Each request allocates a fresh ID. Receiving a response
stores its receive state at another fresh ID, so the original request remains
available and valid responses can still be replayed.

`compromiseCommunicationState participant stateId` exposes the current state
at that address. Communication compromise predicates quantify over IDs and
values, retaining the participant-level compromise exceptions.

Specifications express retained requests directly using
`PersistentLocalUpdateableState.StateWasSet`, together with the metadata
state-handle and server equalities. These historical facts persist on every
trace extension. Equality-only communication updates identify metadata for the
same address on invariant traces and ensure that reads recover the original
request.
The send and receive specifications are ordinary `HoareTriple` instances, available
to `step` without metadata or key-family ghost arguments. Response-send
preconditions quantify over the retained metadata and its authorization and
key-label obligations. Response-receive postconditions identify the retained
metadata uniquely, allowing proofs to recover facts about a known request
witness without a separate specification.

## Combined crypto policies

`Core/Lemmas.lean` and `RequestResponse/Lemmas.lean` provide one specification
family in `DY.Communication`, using usage-dispatched crypto policies. A model
may use a single communication policy or combine several channel policies;
both use the same operations, specifications, and reachability configurations.
The standalone predicate instances have reflexive agreement instances, so
single-policy models do not need a separate specification family.

Supply the global crypto predicates, their byte-invariant components, and the
`EncryptPred.Has` / `SignPred.Has` agreement instances generated by `#combine`.
Encryption keys use `communicationPkeUsage α`, whose kind is `PKEKey`, whose
tag is `pkeKeyName α`, and whose data is `none`. Signing keys use `communicationSignatureUsage α`, whose kind is `SigKey`, whose
tag is `signatureKeyName α`, and whose data is `none`. Ownership remains in the
key labels and state. These are configuration facts, not additional execution preconditions.
Aliases used for registrations must be reducible for instance search, or callers
must install the corresponding concrete agreement instances explicitly.

`HasUsage` also holds for public keys with unrelated actual usages. PKE dispatch
therefore retains a public-plaintext alternative, and AEAD responses retain the
endpoint-compromise alternative. Merely having `HasUsage` never selects a policy.
The split pure decryption helpers need a stored-key usage fact; public receive
specifications derive it from the existing key-store invariant and still require
only `True` from their callers.
